# N3 Standard Audio Modem Design

## Purpose

N3 is a clean transmitter and receiver implementation that reproduces the
wire format generated by `Standardization/example_tx.py`. The executable
reference is authoritative when it conflicts with the accompanying Word
document. N3 keeps AudioModem's robust synchronization, sampling-frequency
offset correction, channel estimation, and diagnostics without changing the
reference waveform.

The existing `modem_n2.py`, `tx_n2.py`, and `rx_n2.py` remain unchanged so
that earlier experiments and recordings stay reproducible.

## Source of Truth

The files in `C:\Users\Administrator\Desktop\Standardization` define the
standard. Precedence is:

1. `example_tx.py` defines the transmitted waveform and processing order.
2. `header_gen.py`, `training_symbol_gen.py`, and `scrambler.py` define their
   respective deterministic algorithms.
3. `Standard document.docx` supplies parameters that do not conflict with the
   executable reference.

In particular, N3 sends one header information block because that is what
`example_tx.py` implements. It does not implement the document's conflicting
three-copy header statement.

The project README and `docs/code_guide.md` will document N3 commands and

## Standard Physical Layer

N3 uses these fixed parameters:

| Parameter | Value |
|---|---:|
| Sample rate | 48000 Hz |
| FFT size | 8192 |
| Cyclic prefix | 2048 samples |
| OFDM symbol length | 10240 samples |
| Active positive-frequency bins | 400 through 2391 inclusive |
| Active subcarriers | 1992 |
| Modulation | QPSK only |
| Bit and byte order | Big-endian |
| Leading training symbols | 8 |
| Trailing training symbols | 8 |
| Chirp duration | 3 seconds |
| Chirp band | 100 Hz to 20000 Hz |
| Chirp type | Linear |
| Silence before and after OFDM | 0.5 seconds |

Positive-frequency QPSK values follow the exact bit mapping in
`example_tx.py`. Negative-frequency bins contain their complex conjugates so
the IFFT output is real. N3 preserves the reference amplitude convention
during mapping and normalizes the complete OFDM region in the same position in
the transmit pipeline as the reference.

## Deterministic Training

Training generation reproduces `training_symbol_gen.py` exactly:

- Python's `random` module is seeded with `80`.
- Sixteen consecutive frequency-domain QPSK symbols are generated.
- The first eight are transmitted before the coded data.
- The final eight are transmitted after the coded data.
- Each symbol receives a 2048-sample cyclic prefix.

The receiver regenerates the same symbols locally. The transmitter may save
the generated array as a diagnostic sidecar, but the sidecar is not required
for decoding.

## Header and File Framing

The first 249-byte LDPC information block contains the header produced by the
reference `header_gen` algorithm. Its layout is:

```text
offset  size  field
0       2     ASCII PH
2       1     protocol version 0
3       4     source file size, big-endian
7       4     payload information-symbol count, big-endian
11      n     UTF-8 filename
11+n    1     zero filename terminator
12+n    4     CRC32, big-endian
remaining     zero padding to 249 bytes
```

The CRC32 covers bytes from offset 0 through the last filename byte; it does
not include the zero terminator. Filenames must fit together with the fixed
fields, terminator, and CRC in 249 bytes. The receiver strips directory
components before writing the recovered file.

The stored payload information-symbol count is
`ceil(file_size / 249)`, equivalent to the reference expression
`ceil(2 * file_size / 498)`.

The 249-byte header block is concatenated with the file bytes. The combined
data is padded with zero bytes to a multiple of 498 bytes, then consumed in
249-byte LDPC information blocks. This preserves the reference behavior in
which the total number of coded OFDM symbols is always even. A final filler
information block may therefore follow the real payload. The receiver uses
the header's file size and payload count and ignores such filler.

N3 does not add the old N2 `AMN2` header, a file CRC field, BPSK header
symbols, permutations, or header voting.

## LDPC and Scrambling

Every 249-byte information block is converted to 1992 big-endian bits and
encoded independently with:

- IEEE 802.16 LDPC;
- rate 1/2;
- expansion factor `Z=166`;
- 3984 coded bits, or 498 bytes, per codeword.

Each coded block is XORed with a newly generated 3984-bit scrambler sequence.
The sequence is reset to seed `0x5A4D` for every block, exactly as in
`example_tx.py` and `scrambler.py`. The scrambled bits are mapped to 1992 QPSK
subcarriers, producing one OFDM symbol per LDPC codeword.

N3 uses the repository's existing LDPC implementation. It removes N2's
802.11n code, extra interleaver, and optional uncoded payload path from the N3
wire format.

## Transmit Data Flow

The transmitter performs:

```text
read file
-> build and pad the 249-byte header
-> concatenate header and file bytes
-> pad the combined stream to a multiple of 498 bytes
-> split into 249-byte information blocks
-> LDPC encode each block
-> reset and apply the scrambler to each codeword
-> map each codeword to one QPSK OFDM symbol
-> place 8 leading and 8 trailing training symbols
-> normalize the OFDM region
-> add identical chirps and 0.5-second silence guards
-> write mono signed 16-bit 48 kHz WAV
```

The final frame is:

```text
3 s chirp
0.5 s silence
8 leading training OFDM symbols
coded header and payload OFDM symbols
8 trailing training OFDM symbols
0.5 s silence
3 s identical chirp
```

The command accepts an input file and output path. QPSK, LDPC, trailing
training, and all physical parameters are mandatory rather than selectable
protocol modes.

## Receive Data Flow

The receiver performs:

```text
validate WAV
-> detect front and rear chirp candidates
-> form physically valid chirp pairs
-> refine OFDM timing with the known leading training block
-> estimate coarse and fine sampling-frequency offset
-> locate the trailing training block from the chirp pair and OFDM grid
-> estimate the channel from valid leading and trailing training symbols
-> demodulate and descramble the first coded data symbol
-> LDPC decode and validate the header
-> decode the stated number of payload information blocks
-> truncate to the stated file size
-> write the recovered file and diagnostics
```

The robust AudioModem receiver behavior is retained where it does not alter
the standard:

- multiple chirp candidates and joint front/rear pair ranking;
- training-based fine timing;
- coarse and fine SFO search with open-loop phase correction;
- channel estimation from both training blocks when available;
- safe fallback to leading training when the trailing block is damaged;
- candidate scoring using training residual, LDPC convergence, header magic,
  version, length plausibility, and header CRC;
- batch receive support and detailed metrics.

The N3 receiver is not required to decode the old N2 format. The existing N2
receiver remains available for that purpose.

## Outputs and Diagnostics

The transmitter writes the WAV and deterministic metadata describing frame
offsets, standard parameters, LDPC block counts, payload size, and applied
gain. It may also write training/header sidecars for experiment inspection.

The receiver writes:

- the recovered file after a valid header and complete payload decode;
- `metrics.json` with chirp scores, timing, SFO, LDPC iterations, header
  status, recovered length, and error details;
- `summary.csv` with per-subcarrier channel magnitude and training error;
- `H.npy`, training phase-fit data, and equalized payload symbols;
- `decoded_header.bin` and `decoded_payload.bin` for diagnosis.

When a source file is supplied, the receiver also reports payload bit and byte
error rates plus exact file-match status. These diagnostics do not affect the
wire format.

## Validation and Error Handling

The transmitter rejects a missing input, an overlong UTF-8 filename, a file
that cannot be represented by the four-byte size field, or an output path it
cannot write.

The receiver rejects non-mono, non-16-bit, or non-48-kHz WAV input. Candidate
failures remain isolated so another chirp pair or SFO hypothesis can still be
tested. It never publishes a recovered file unless the header magic, version,
lengths, and header CRC pass and enough payload blocks were decoded. Failures
produce diagnostics and a nonzero command exit status.

Because the reference header contains no file CRC, exact payload integrity is
only provable when a source file is supplied. Without one, successful LDPC
decoding and a valid header are reported separately from end-to-end file
verification.

## Test Strategy

`tests/test_n3.py` will cover deterministic and end-to-end behavior:

1. Header bytes match `header_gen.py` for fixed filenames, sizes, and symbol
   counts.
2. Scrambler prefixes and full-block hashes match `scrambler.py`.
3. All sixteen training symbols match `training_symbol_gen.py` for seed 80.
4. QPSK mapping, big-endian bit order, conjugate symmetry, cyclic-prefix
   placement, and OFDM dimensions match the reference.
5. LDPC code parameters are 802.16, rate 1/2, and `Z=166`; encoded blocks
   satisfy the parity-check matrix and decode without channel errors.
6. Frame offsets, training placement, coded block count, silence, and chirps
   match the standard structure.
7. A small file completes an offline transmit/receive round trip.
8. The receiver handles deterministic gain, leading delay, and light seeded
   noise without changing the decoded file.
9. Invalid WAVs, corrupted headers, truncated recordings, and excessive
   filenames fail explicitly.
10. `python -m py_compile` succeeds for all N3 entry points.

During development, reference-equivalence checks may import files directly
from `Standardization`. Committed tests will store compact golden values so N3
remains self-contained.

## Documentation and Compatibility

`n3/README.md`, the project README, and `docs/code_guide.md` will describe the
standard command line, frame structure, generated artifacts, and verification
commands. Existing N1 and N2 documentation remains identifiable as legacy
experiment guidance.

No archived data or existing N2 files are deleted or rewritten. Generated N3
WAVs and receiver outputs stay under `data/n3/` and `runs/n3/`.
